## С чего начать

Прочитайте [README](README.md) и [кодекс поведения FORQO](CODE_OF_CONDUCT.md). Помочь можно кодом, переводом, документацией, воспроизводимым сообщением об ошибке или проверкой существующего изменения.

Для небольшого исправления можно сразу открыть PR. Крупную функцию, изменение архитектуры или формата данных сначала обсудите в Issue, чтобы согласовать задачу и границы работы.

## Сообщить об ошибке или предложить идею

О предполагаемой уязвимости сообщайте по [политике безопасности FORQO](SECURITY.md). Не раскрывайте её технические детали в обычном Issue или публичном PR.

Используйте [формы Issues](https://github.com/FORQO/DiscForge-RU/issues/new/choose):

- **Ошибка · FORQO:** фактический и ожидаемый результат, шаги воспроизведения, версия и окружение.
- **Предложение · FORQO:** задача пользователя, предлагаемое решение, критерий успеха и альтернативы.

Перед отправкой посмотрите похожие обращения. Приложите минимальный искусственный пример; удалите личные данные, токены, пароли и конфиденциальные материалы из текста, журналов и вложений.

Если вопрос относится к другой программе FORQO, создайте Issue в её репозитории.

## Подготовка изменения

Работайте в отдельной ветке. Для публичного репозитория можно использовать fork; для закрытого нужен уже предоставленный доступ. Не меняйте настройки доступа ради отправки вклада.

Обычная базовая ветка — `main`; если исправление относится к другой рабочей ветке, укажите её явно.

```sh
git clone https://github.com/FORQO/DiscForge-RU.git
cd DiscForge-RU
git switch -c fix/short-description
```

Нужны Python 3.11+ и виртуальное окружение. Установите зависимости и запустите приложение:

```sh
python -m pip install -r requirements.txt
python main.py
```

## Проверки

```sh
python -m unittest discover -s tests -v
```

Для изменений конвейера проверяйте короткие искусственные медиа-примеры. Изменения меню требуют проверки предпросмотра и итоговой сборки; запуск в VLC не подтверждает работу на всех физических проигрывателях. Публикация Windows-сборок описана в [PUBLISH_GITHUB.md](PUBLISH_GITHUB.md).

Запускайте проверки, относящиеся к изменению, и соблюдайте дополнительные обязательные требования проекта. В PR укажите команды, платформу и результат. Недоступные или не запущенные проверки перечисляйте отдельно с причиной.

Для изменения интерфейса добавьте скриншоты до / после на демонстрационных данных. Для изменения поведения опишите воспроизводимый сценарий; если есть тестовый набор, добавьте проверку, которая обнаруживает исправляемую проблему.

## Особенности проекта

Сохраняйте совместимость существующих проектов, возможность отмены и повторного запуска сборки. Не добавляйте большие фильмы, личные пути и результаты сборки. Технические ограничения и статус macOS сверяйте с README и документацией.

## Pull Request и review

Одна задача — один PR. Старайтесь отделять исправление от массового форматирования, переименований и необязательных переделок.

Заполните [PR-шаблон](.github/PULL_REQUEST_TEMPLATE.md):

1. Какая задача решается и что меняется для пользователя.
2. Какие Issues связаны с изменением. Используйте `Closes #...` только для полностью решённой задачи.
3. Какие проверки выполнены и что осталось непроверенным.
4. Какие инструкции, платформы, данные и сценарии совместимости затронуты.
5. Какие ограничения остаются.

Заголовок PR должен описывать результат. В коммитах объединяйте связанные изменения; сохраняйте историю и авторство участников. Если в репозитории есть дополнительные правила коммитов, следуйте им.

В review отвечайте по существу, обновляйте описание при изменении объёма PR и соблюдайте [CODE_OF_CONDUCT.md](CODE_OF_CONDUCT.md). Предложение рассматривается с учётом целей и текущего состояния проекта; открытие PR не гарантирует его принятие.
